EASD Transcription App: v8.9 Fix Report

Branch v8.9 · 28 October 2026 · All changes are in the working tree and not committed. Review them, then commit.

Summary

The app was meant to do four things:

  1. Take bulk recordings or a live recording.
  2. Transcribe them word for word, with timestamps and who is speaking.
  3. Optionally convert that to English only or Bangla only.
  4. Fill the EASD .docx template from the transcript.

Before this release, step 3 did not exist and speaker labels were guesses. Both now work: speakers are identified by voice, using a local AI model that runs on this computer. The remaining items from the bug report are also fixed, Intel/AMD/NVIDIA GPU acceleration has been added, and the screen has been made easier to use on PC, tablet and phone.

Verified on the running app: Bangla→English and English→Bangla conversion through Gemini (timestamps and speakers unchanged), live preview with the new timeline, voice-based speaker labels (4 voices labelled 1-2-3-1-2-3 correctly), matching speakers across chunks, the attendance fix, and the CORS lock-down.

1. English-only / Bangla-only conversion CriticalNew feature

Problem

The app could only show the transcript as spoken (mixed Bangla and English). There was no way to get an all-English or all-Bangla version, and nothing in the code attempted it.

What was done

A new translation module, an API endpoint, and three tabs above the transcript box: As spoken · English only · বাংলা only.

How it works, step by step
  1. The transcript is split into lines. The [MM:SS] Speaker N: part of each line is set aside and is never sent to the AI, so timestamps and speaker labels cannot be changed or lost.
  2. Lines that are already entirely in the target language are skipped. This saves time and money, and those lines stay exactly as spoken.
  3. The remaining lines are sent in numbered batches (up to 40 lines or 6,000 characters each). The AI must return exactly the same number of lines, in order.
  4. If a batch comes back with the wrong number of lines, that batch is retried one line at a time. If a single line still fails, it keeps its original wording and the user sees a warning naming the line numbers. Nothing is silently dropped.
  5. The prompt tells the model to keep names, numbers, dates, amounts and acronyms (EASD, Q4…) exactly, and not to summarise or add anything.
  6. The prefixes are re-attached, and the result appears in the chosen tab.
How to use it
  1. Transcribe or paste the meeting.
  2. Click English only or বাংলা only. The first click converts; later clicks just switch tabs.
  3. Edits in that tab stay in that version; the "As spoken" record is never overwritten.
  4. Fill Template uses whichever tab is showing, so you can fill the minutes from the English or Bangla version.
  5. If you edit the "As spoken" text afterwards, a yellow note says the converted version is out of date. Press Convert again to refresh it.

It uses the same AI setting as Fill Template: Gemini by default, your Custom API if one is selected, or the on-device model when the Cloud/Local switch is set to Local.

2. Real speaker identification, using a local model Critical

Problem

In local Whisper mode, "Speaker 1 / Speaker 2" was a guess: the label flipped every time someone paused for more than 1.6 seconds. Meetings with three or more people only ever showed two speakers, and a pause mid-sentence handed the rest of the sentence to the "other" person.

What was done

A new module, speaker_diarization.py, identifies speakers by their voice using WeSpeaker ResNet34. This is a 26 MB neural speaker-recognition model that runs on this computer, with no internet, no API key and no extra large packages (no PyTorch). It is downloaded once into models/; that has already been done on this PC.

How it works, step by step
  1. Whisper produces the utterances with start and end times, as before.
  2. For each utterance, the module computes a "voice fingerprint", a 256-number embedding produced by the neural model from that stretch of audio.
  3. Fingerprints that are close together belong to the same person. The utterances are grouped step by step (average-linkage clustering, cosine distance) until the closest remaining groups are clearly different voices. The cut-off, 0.55, was calibrated on test voices: same voice ≈ 0.26–0.42, different voices ≈ 0.69–1.06.
  4. Very short utterances (under 0.8 s) are too short to judge on their own. They are given the nearest known voice, or the previous speaker.
  5. Speakers are numbered in the order they first speak: Speaker 1, 2, 3…
  6. If the model cannot load, a simpler built-in voice fingerprint (MFCC) is used instead. If anything goes wrong, transcription still succeeds and only the labels are less precise.
Verified

On a test recording of 4 different voices in the order A B C A B C, the result was [1, 2, 3, 1, 2, 3], which is exactly right. Each utterance takes about 0.12 s on this PC's CPU, and less on a GPU.

Files

speaker_diarization.py (new) · local_whisper_engine.py (pause-flip removed, voice labelling added)

3. Speaker numbers are now consistent across chunks Critical

Problem

Long recordings are split into chunks of about 10 minutes, and each chunk is transcribed separately (by Gemini or Whisper). Every chunk restarted the numbering at "Speaker 1", so Speaker 1 in chunk 2 could be a different person from Speaker 1 in chunk 1.

How it was fixed, step by step
  1. After all chunks are transcribed, each chunk's audio is decoded to 16 kHz WAV.
  2. For every chunk and local speaker (for example "chunk 2, Speaker 1"), up to 90 seconds of that person's speech is collected and turned into one voice fingerprint with the same local model.
  3. These fingerprints are grouped across chunks. One rule applies: two speakers that the chunk itself already said are different people can never be merged.
  4. Every line is relabelled with one consistent numbering for the whole meeting.
  5. If anything fails, the per-chunk labels are kept, and the transcript is never lost.
Verified

Test: chunk A had voices X then Y; chunk B had Y then X, both numbered 1 and 2 locally. After the fix, chunk B reads "Speaker 2, Speaker 1", which correctly matches chunk A.

Files

stt_pipeline.py (_unify_speakers_across_chunks) · speaker_diarization.py (unify_chunk_speakers)

4. Timestamps no longer fall back to [00:00] Critical

Problem

When Gemini returned an utterance without word timings, the line was stamped [00:00], so lines in the middle of a meeting appeared at the very start.

Fix

A line without its own timing now takes the time of the line before it. Time can never go backwards within a chunk, and the chunk's start offset is still added afterwards. Text that appears before the first timestamp correctly starts at the beginning of its chunk.

File

stt_pipeline.py (_lines_from_transcribe_response)

5. Live recording: one timeline, the live model, and no freezing Critical

Problems
  • Every 4.5 seconds the browser re-sent and re-transcribed the whole recording so far. Cost and delay grew with every minute, and the same text had to be filtered out again each time.
  • Timestamps restarted from zero in every preview.
  • The live code ignored the chosen model and always used gemini-2.5-flash.
  • The WebSocket live endpoint called the slow transcription function directly, which froze the whole server (progress bars, other uploads) during every chunk.
How it was fixed, step by step
  1. The browser now also sends offset_sec, the number of seconds already previewed.
  2. The server converts the recording to WAV, cuts off everything before offset_sec, and transcribes only the new audio.
  3. The returned lines are shifted onto the recording's own clock, for example [03:12] Speaker 1: …, and the server returns end_sec. The browser stores this and sends it as the next offset.
  4. The live preview uses gemini-3.5-transcribe-live, or your chosen Whisper model, with the same Gemini → fallback-model → local-Whisper safety chain as batch transcription.
  5. Both live endpoints now run the work in a background thread, so the server stays responsive.
  6. When you press Stop, the full take is still transcribed again with the batch model. That final pass gives the definitive voice-matched speaker labels.
Verified

A 7-second test file sent with offset_sec=3 returned only [00:03] Speaker 1: Today we discuss the budget and strategic review. with end_sec=7.25.

6. Template fill now reports failures High

Problem: /api/summarize_transcript always answered "success", even when the AI step had returned an error, so the screen claimed the template was filled when it was not.

Fix: the endpoint now checks the result. On failure it returns status: "error" with the reason, and the UI shows a red message. The upload endpoint already did this; the two now behave the same.

File: app.py. Covered by the new test test_summarize_reports_error_status.

7. No more shared transcript file on disk High

Problem: every local transcription wrote raw_transcript.txt into the app folder. Two jobs running together overwrote each other, and confidential meeting text stayed on disk.

Fix: the file is no longer written. For troubleshooting, set EASD_DEBUG_SAVE_TRANSCRIPT=1. A separate copy per job is then saved in the system temp folder.

File: local_whisper_engine.py. You may delete the old raw_transcript.txt in the app folder; it is not used any more.

My first bug report said the meeting-minutes template had no section keys. That was my mistake: sections use the field id, not key, and I read the wrong field. On re-checking, easd_default_minutes correctly maps agendas, decisions, the discussions table (4 fixed rows) and the attendance table to the EASD .docx. No change was made.

9. Attendance: false "present" marks High

Problem, corrected: the original report said attendance was always "Yes". In fact the app does detect attendance, but its matching was too loose. Any single word of four or more letters from a member's name counted, so one mention of "Hossain" or "Islam" marked several different members present.

Fix, step by step: a member is now marked present only if the transcript contains, as whole words, one of the following:

  • their full name;
  • at least two parts of their name;
  • one part of their name that no other member shares. Common surnames such as Hossain, Islam, Begum, Akter, Hasan and Kumar never count on their own.

Names the AI explicitly lists as present still count as before.

Verified: the text "Saddam Hossain presented… Kartik said ok… Mr Islam was absent" now marks exactly Md. Saddam Hossain and Kartik Bala.

File: ai_providers.py (match_attendance_list)

10. API keys were readable by any website High

Problem, clarified: the server already listens only on this computer (127.0.0.1). However, its CORS rule allowed every website origin with credentials. Any web page open in the same browser could therefore call localhost:8000/api/settings and read the saved API keys.

Fix: only the app's own pages (localhost, 127.0.0.1, any port) are allowed. To use the app from another device, add its address with EASD_ALLOWED_ORIGINS=https://192.168.1.20:8000.

Verified: a request from https://evil.example gets no permission header, so the browser blocks it. http://localhost:8000 is still allowed. File: app.py

TurboQuant: Tom's fork Optional

What it is: TheTom's llama.cpp fork (github.com/TheTom/llama-cpp-turboquant, branch feature/turboquant-kv-cache) adds TurboQuant KV-cache types (turbo3, turbo4). They compress the local LLM's working memory roughly 4–5× with very small quality loss.

Important: TurboQuant applies only to the local LLM (template fill and translation). It does not speed up Whisper or speaker identification. Its main benefit is lower memory use, which helps on iGPUs that share system RAM, rather than raw speed.

What was done:

  1. local_llm_engine.py accepts EASD_LOCAL_LLM_KV_CACHE=q8_0 | turbo3 | turbo4. The type IDs (turbo3 = 44, turbo4 = 47) were taken from the fork's own ggml.h.
  2. TurboQuant is opt-in only, because a normal llama.cpp build may crash on an unknown cache type. q8_0 works on every build and already halves memory.
  3. Build scripts that compile llama-cpp-python against the fork with GPU support: scripts/build_llama_turboquant.sh [vulkan|cuda|metal|cpu] and scripts\build_llama_turboquant.bat for Windows.

Not yet run: the fork build itself (it takes a long time and needs build tools and the Vulkan SDK). If the fork's code has moved ahead of llama-cpp-python, the build can fail. In that case, restore with .venv/bin/pip install --force-reinstall llama-cpp-python.
